# Greenfield database — isolated prototype
- PostgreSQL 16 (test baseline, not final production version), disposable GitHub-hosted runner, synthetic fixtures only; no ports published, no production connection strings, no repository secrets, no remote host, no deployment.
- Apply migrations in numeric order once to a new database named upc_greenfield_test. Migration 0001 is intentionally restricted by database name; not a production migration. CI uses ephemeral container with trust authentication only inside the disposable service; production must use secure authentication, dedicated NOLOGIN owners and least privilege.
- 0001 establishes core tenants/users, memberships, private database-login binding, canonical customers, verified identity and addresses. A customer is tenant-owned, not store-owned. Composite FK blocks mismatched tenant relationships. Unique active verified identity scoped to tenant; distinct verified identifiers may still belong to the same person; cross-identifier linking, identity proof, ambiguity/merge workflow and audit are pending. Never assume phone alone proves identity.
- Provisional session_user mapping avoids spoofable tenant GUC. This is a trusted backend prototype, not an approved login-per-user/tenant pooling architecture. Direct runtime reads intentionally limited to these prototype tables; no direct customer writes; verifier role is trusted and must independently prove identity before calling. SECURITY DEFINER functions owned by test bootstrap superuser only in disposable CI; before release replace with hardened non-superuser owner and explicit privilege/RLS design. Do not expose these roles to end users.
- Tests cover sequential same-key reuse, different tenants, unique verified key, invalid input rollback, cross-tenant FK, denied direct write and verification, private mapping, forged GUC, unmapped session and membership revocation. Concurrency, RLS write checks, per-user IAM/module approval, audit, and broader domains remain pending. No production ready claim.
- CI proof is a successful Actions run for a specific commit, not existence of test files. Check logs before reporting PASS.

## 0002 — provisional IAM/module approval
- Non-login non-superuser NOBYPASSRLS function owners separate lookup, CRM writer, policy reader and module decision execution. Bootstrap table ownership remains test-only. Runtime cannot inherit these owners.
- Role permissions are tenant-scoped through composite FK; core users shared only as identity accounts. Platform staff assignments are separate from tenant membership. Permission queries default deny. Module registry is single; append-only decisions are both the approval record and the source of current enablement; latest decision wins even when expired/revoked. No mirrored enable flag. Decision actor and reason required.
- Bootstrap provisions roles/grants/staff only; delegated role-management API, explicit approval request workflow, module version history, generalized audit and superadmin audited cross-tenant read are still pending. Permission/module queries are implemented but existing CRM runtime grants are NOT yet gated by them; do not expose this as complete authorization. Next: wire enforcement to CRM and subsequent domains, add concurrency tests and verified cross-identifier linking.

## 0003 — CRM enforcement
The previous ungated CRM grants are now restricted by tenant RLS plus crm.read or crm.write and a current CRM module decision. Verified identity linking uses the same per-identity transaction lock as resolution; conflicting ownership is rejected, not merged. Verification itself remains the responsibility of a trusted service; normalization beyond existing constraints, audit events, merge review and production connection design remain pending. The concurrency test observes actual lock contention on two sessions. CI tests run on a fresh isolated database; older fixtures updated for the new mandatory grants.

## 0004 — tenant catalog and temporal prices (provisional)
One tenant-owned product master, variants with tenant-unique case-insensitive SKU, flat categories with relation, price lists and effective-dated price entries. Currency is fixed on each price list; amount is stored only in entries. PostgreSQL btree_gist exclusion prevents overlapping price periods for one tenant/variant/list. Runtime cannot overwrite historical amounts or move period start; it may shorten the end and insert the next price in one transaction. Product/variant/list activation affects price_at; direct price history reads remain permission-gated. Category hierarchy, shared media assets, currency registry/minor-unit rounding, price-list audience/selection, channel policies, and business rules on retroactive period closing need further design; current model does not claim complete accounting or audit. No duplicate product master, inventory quantity or sales order tables.

## 0005 — inventory prototype
Three tables: warehouses, append-only signed stock ledger and reservations; stock_balances is a security-invoker derived view, not a second inventory master. Tenant-aware catalog/warehouse FKs, per-tenant idempotency keys with payload conflict detection, one ledger movement per consumed reservation, actor attribution and permission/module gates. Only narrow non-login SECURITY DEFINER executor mutates ledger/reservation. Shared advisory transaction lock per tenant/warehouse/variant serializes adjustments and reserve/release/consume; READ COMMITTED required, higher isolation rejected to prevent stale snapshot oversell. Expired active reservations cease holding stock and cannot be consumed. Full consumption only, no backorders. Tests use synthetic fixtures and concurrent sessions. Provisional: integer units, physical products only, no transfer, lot, serial, valuation, partial fulfillment, automated expiration cleanup, order association or multi-pair lock ordering yet; historical corrections are new movements. Availability is statement-time derived; do not treat it as a reservation guarantee. Production scalability/security and lifecycle decisions remain open.

## 0006 — sales prototype
Three tables: orders, immutable order items (price/SKU/name snapshots), and verified full captures. Order total derived from lines, not independently editable. Tenant-aware FK to existing customer, warehouse, price list, exact variant/price and reservation quantity. Checkout takes expected price, validates server-side effective price and reserves stock atomically in sorted variant order. One canonical checkout key per tenant; payload mismatch rejected. Order-owned reservation namespace is restricted to sales; direct inventory release/consume and internal entry points denied to runtime. One full positive capture per order; separate trusted recorder DB role plus permission/module; provider/account/reference scoped uniqueness, exact amount/currency and retry consistency. Does not charge or verify a real gateway; trusted service must independently authenticate captures. Paid orders can fulfill all holds atomically, unpaid orders cancel/release. Capture after hold expiry can be recorded for a pending order, but fulfillment is blocked; cancelled-order or extra captures require external reconciliation. Provisional: physical goods, single warehouse/list/currency, whole units, positive total, no taxes/discounts/shipping, partial payments, refund, late-payment recovery, digital/service delivery, detailed state-event audit or concurrent sales test yet. Never expose payment recorder to untrusted clients. No production readiness claim.
