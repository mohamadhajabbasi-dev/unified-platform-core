## پیشنهاد آزمایشی
Two dependent relations, not duplicate masters:
- catalog.attribute_definitions: tenant_id, attribute_id UUID, stable ASCII lowercase key, display_name, server created_at; PK tenant+attribute, unique tenant+key. Proposed technical bounds key 1..80, display label 1..120 nonblank, case-insensitive display-name uniqueness only if justified by duplicate avoidance (no mandatory translation policy). No rename/type change/delete yet; immutable definition registration exact replay if same key+label, conflict otherwise.
- catalog.variant_attribute_values: tenant_id, assignment_id UUID, variant_id, attribute_id, value_text, created_at, changed_at. Composite FKs to existing variants and definitions; unique tenant+variant+attribute. One current textual descriptive value per attribute per variant (e.g., color, size), not an option dictionary and no duplicate copy in SKU, product, name or JSON. Preserve meaningful case and internal whitespace, reject empty/whitespace-only/control and overly long text (proposed 1..512); do not normalize locale or define numeric units implicitly. Index tenant+attribute+variant for filtering; no speculative GIN index. No automatic variant generation or unique combinations; two existing variants may have same descriptive values. No parent-product inheritance/fallback, product-level attributes, typed/ranged values, controlled vocabularies, translations, display order, indexing for public search, clear/remove/reassign semantics unless designed separately; do not claim these complete. Product-level future should reuse the same definitions, not a parallel definition dictionary.
